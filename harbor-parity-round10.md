### 1. Hard email regression: response-envelope contract drift

**Reproduction**:
1. Plan3's Bun mock-email handles `POST /api/auth/login` in `mock-platform/mocks/email/src/routes/auth.ts:104`:
   ```ts
   return c.json(ok({ message: "Login successful", user, access_token: accessToken },
                    "Login successful"));
   ```
   The `ok()` helper from `mock-lib` produces:
   ```json
   { "success": true, "message": "Login successful",
     "data": { "message": "Login successful", "user": {...}, "access_token": "..." } }
   ```
2. The legacy `email-app` frontend at `tasks/<task>/environment/email-app/frontend/src/context/AuthContext.jsx:40` still does:
   ```jsx
   const response = await authAPI.login(username, password);
   const { access_token, user } = response.data;       // destructures from response.data
   localStorage.setItem('token', access_token);        // stores "undefined"
   setUser(user);                                       // sets undefined
   ```
   Because `response.data` is now the envelope (`{success, message, data}`), neither `access_token` nor `user` exist at that level — both come back `undefined`.
3. `localStorage.setItem('token', undefined)` stores the literal string `"undefined"`. Every subsequent request fails 401, and the agent sees a permanent login wall.

**Evidence the frontend was never updated**:
- 9 copies of `email-app/frontend/src/context/AuthContext.jsx` exist across tasks (email-* + flight-* tasks that need the inbox for notification).
- All 9 are byte-identical (MD5 `286b9ca7d3386c350a81f95d071a7dc0`).
- The plan3 copy is byte-identical to the `main-baseline` copy — i.e. the mock migration changed only the Bun backend, never the legacy React frontend code.

**Trace from migrated `email-reply__GmuDRRc/agent/openclaw.txt`**:
> "I see a login page for the email system. I need credentials to access it. Do you have a username and password for your company email system?"

Compare with baseline `email-reply__eMXzKWh/agent/openclaw.txt`:
> "I can see there's an email from "lau.pai" from Parrot AI in the inbox. Let me click on it to read the full content."

Identical model (MiniMax-M2.5), identical credentials wired via `MOCK_CREDENTIALS` autoLogin path — the only difference is that baseline's Flask backend returned `{access_token, user}` at the top level, while plan3's Bun mock wraps it one level deeper.

### 2. python_compat shim architecture (why the verifier still passes import-check)

Plan3 removed `pip install -r requirements.txt` and `python3 app.py` from `tasks/email-reply/environment/Dockerfile` (commit `e2a03b0`), but the **verifier still imports the Flask app for reward calculation**. The migration solves this with a runtime shim, visible in `mock-platform/dist/startup-email-reply.sh`:

```bash
ln -sfn /opt/mock/python_compat/email-app /workspace/environment/email-app
mkdir -p /workspace/environment/email-app/backend/instance
ln -sf /var/lib/mock-data/email/email.db \
       /workspace/environment/email-app/backend/instance/email.db
python3 -c "import sys; sys.path.insert(0, '/workspace/environment/email-app/backend'); \
            from app import app; from models import Email"   # import-check only
/opt/mock/bin/mock-email --port 5001 > /tmp/email-backend.log 2>&1 &
```

So the architecture is:
- `/opt/mock/python_compat/email-app/` — Flask source preserved at image build time, used **only** for `from app import app` so the verifier (which runs `verify.py` with `sys.path.insert` to email-app/backend) keeps working.
- `/opt/mock/bin/mock-email` on port 5001 — Bun binary, real backend serving both API and statically built frontend (a TCP forwarder bridges legacy port 5174 → 5001).

The shim keeps the verifier green but **the frontend that ships to the agent's browser is still the legacy React build** that hasn't been adapted to the new envelope. That asymmetry is exactly the regression surface.

### 3. Why airline tasks are immune (and even improved)

Examined `tasks/flight-booking/environment/airline-app/frontend/src/context/AuthContext.jsx`:
```jsx
const fetchProfile = async () => {
  const response = await authAPI.getProfile();
  setUser(response.data.data);            // already unwraps the `data` field
};
const value = {
  user, loading, updateProfile,
  isAuthenticated: true,                  // no JWT flow — always authenticated
};
```

Two reasons it didn't break:
1. **No login destructure**: airline-app uses a profile-fetch model, never `const { access_token } = response.data`.
2. **`isAuthenticated: true` hardcoded**: there's no token validation gate at all.

The baseline 0.0 → migrated 0.5+ jumps on the 3 flight tasks are unrelated to the envelope migration. Commit `f7aa19f` replaced fixed `sleep` in flight task startup scripts with health-check polling (`wait_http`) — baseline was racing the Flask boot on slow Docker hosts; plan3 deterministically waits, so the agent now reliably finds the app on first try.

### 5. Recommended fix

**One-line change, replicated across 9 files** (all byte-identical):

```diff
- const { access_token, user } = response.data;
+ const { access_token, user } = response.data.data;
```

Affected paths (all identical content, MD5 `286b9ca7d3386c350a81f95d071a7dc0`):
- `tasks/email-reply/environment/email-app/frontend/src/context/AuthContext.jsx`
- `tasks/email-writing/environment/email-app/frontend/src/context/AuthContext.jsx`
- `tasks/email-washer-change/environment/email-app/frontend/src/context/AuthContext.jsx`
- `tasks/email-watch-shop/environment/email-app/frontend/src/context/AuthContext.jsx`
- `tasks/schedule-change-request/environment/email-app/frontend/src/context/AuthContext.jsx`
- `tasks/flight-cancel-claim/environment/email-app/frontend/src/context/AuthContext.jsx`
- `tasks/flight-info-change-notice/environment/email-app/frontend/src/context/AuthContext.jsx`
- `tasks/flight-seat-selection/environment/email-app/frontend/src/context/AuthContext.jsx`
- `tasks/flight-seat-selection-failed/environment/email-app/frontend/src/context/AuthContext.jsx`

Three destructure sites need the change (lines 40, 58, 71). Line 24 (`setUser(response.data.user)`) also needs `response.data.data.user`.

**Alternative considered (and rejected)**: have the auth route in `mocks/email/src/routes/auth.ts` return an unwrapped shape using a bespoke response helper. This would deviate from the project-wide `ok()/err()` contract documented in `mock-platform/docs/mock-conventions.md`, undoing one of the migration's main goals. Fixing the 9 frontend copies is the smaller blast-radius.

**Optional follow-up**: dedupe the 9 byte-identical copies via a build-time symlink or shared package, so the next contract change touches one file instead of nine.

### 6. Statistical caveats

The noise floor failed: mock-independent P75 |Δ mean| = 0.223 (threshold 0.10), driven primarily by `vue-build-fix-single` (0.963 → 0.37) and `skill-supplementation` (0.556 → 0.333). Per the plan's gating rule, this means the soft regressions (≈0.33 deltas on `email-washer-change`, `email-watch-shop`, `watch-shop`) are provisional and should be re-tested with `--n-attempts 6` before final attribution.

**However, the hard regressions are unambiguous at any sample size**: 3/3 = 0.0 on both `email-reply` and `email-writing`, max delta = −1.0 each. There is no statistical scenario under which two tasks independently produce 6 consecutive zeros against a baseline of 6 consecutive ones from sampling noise. The auth-wall mechanism above is the explanation and the fix above resolves it.

1. **Block merge until fix is applied** — auth wall is a hard regression on a core agent capability (email).
2. **Apply the `response.data.data` patch** to all 9 `AuthContext.jsx` copies; re-run the 9 affected tasks with `--n-attempts 3` to confirm.
3. **Optionally re-run mock-independent cohort with `n=6`** to firm up the noise floor and discharge the `watch-shop` / soft-email FAILs.
